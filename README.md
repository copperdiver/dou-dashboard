# DOU Dashboard

Заготовка приложения: Next.js (App Router) + PostgreSQL, фоновые задачи по
расписанию в отдельном контейнере и дашборд со статистикой их выполнения.

## Стек

| Слой | Решение |
|---|---|
| UI и SSR | Next.js 16 (App Router), React 19, Tailwind CSS 4 |
| БД | PostgreSQL 18, Drizzle ORM + drizzle-kit для миграций |
| Очереди и расписание | BullMQ + Redis 8, воркер в отдельном контейнере |
| Запуск | Docker Compose: `postgres`, `redis`, `migrate`, `web`, `worker` |

## Быстрый старт — всё в Docker

```bash
cp .env.example .env
docker compose up -d --build
```

Дашборд: http://localhost:3000

Что происходит: поднимаются Postgres и Redis, одноразовый сервис `migrate`
включает расширения `pg_trgm`/`unaccent`, применяет миграции, заливает
справочники (250 стран с алиасами, 27 штатов, категории и атомарные причины
отказа) и завершается. Затем стартуют `web` и `worker`.

Справочники — не демо-данные: без них не сопоставляются страна рождения
и штат проживания, поэтому они часть развёртывания, а не отдельный шаг.

## Разработка на хосте

В Docker остаётся только инфраструктура, Next.js и воркер запускаются локально
с hot-reload:

```bash
cp .env.example .env
docker compose -f docker-compose.dev.yml up -d
npm install
npm run db:migrate
npm run db:seed-reference

npm run dev          # терминал 1 — http://localhost:3000
npm run worker:dev   # терминал 2 — фоновые задачи
```

## Конвейер загрузки

Прогресс живёт в таблицах Postgres, а BullMQ — только будильник. Каждая
задача — идемпотентный насос: забирает пачку работы через
`for update skip locked`, обрабатывает и завершается. Перезапуск воркера
или `docker compose down -v` для Redis не рушат бэкфилл на 250 дней.

| Насос | Очередь | Что делает |
|---|---|---|
| `discover` | jobs | ставит в `ingest_days` дни за последнюю неделю |
| `enumerate` | fetch | дневной индекс → снапшот `jsonArray` → список статей |
| `fetch` | fetch | загрузка страниц в `source_page_html` |

Очереди разделены по классу ресурса, а не по шагу: в BullMQ concurrency и
limiter задаются на Worker. `dou-fetch` — единственная, что ходит в сеть:
concurrency 1 и один запрос в 2 секунды. У насосов `attempts: 1` —
«повтор» это следующий тик крона, а учёт попыток по единице работы живёт
в самой таблице (`attempts`, `next_attempt_at`).

Сбои различаются по типу, а не сваливаются в один ретрай:

| Ответ источника | Реакция |
|---|---|
| 403 / 429 | пауза всей очереди `dou-fetch`; попытка не сжигается; серия из 3 → пауза на час |
| 404 / 410 | `fetch_status='gone'`, больше не пытаться |
| 5xx, таймаут | экспоненциальный backoff, после 5 попыток `failed` |
| 200 без `script#params` | `failed` с явным «разметка изменилась» — этот сигнал нельзя глушить ретраями |
| дневной индекс пуст | `no_edition` (выходные, праздники), а не `failed` |

Бэкфилл и инкрементальный опрос — один и тот же код. Различаются только
`origin` (для отчётности) и `priority`: насос берёт
`order by priority, edition_date desc`, поэтому свежий день никогда
не ждёт, пока дожуётся история.

Один прогон насоса — одна строка в `job_runs`; детали в `meta`
(`{days, pages, noEdition, failures, schemaMismatch}`). Журналом
элементов `job_runs` не становится.

## Как добавить фоновую задачу

1. Опишите её в `SCHEDULE` в `src/worker/jobs.ts` — имя, очередь,
   cron-выражение, описание.
2. Добавьте обработчик в `handlers` под тем же именем.
3. Перезапустите воркер — расписание синхронизируется автоматически,
   удалённые из `SCHEDULE` задачи снимаются с расписания.

```ts
// src/worker/jobs.ts
export const SCHEDULE = [
  { name: 'import-orders', queue: 'jobs', pattern: '*/10 * * * *', description: 'Импорт заказов' },
]

export const handlers = {
  async 'import-orders'({ log }) {
    const orders = await claimOrders() // работу берём из БД, а не из payload
    log(`получено ${orders.length}`)
    return { itemsProcessed: orders.length, meta: { orders: orders.length } }
  },
}
```

Насос обязан быть идемпотентным и брать работу из БД, а не из payload
задания: только тогда лишний или повторный запуск безвреден, а прогресс
переживает потерю Redis. Если источник попросил подождать, верните
`cooldownMs` — воркер поставит очередь на паузу, не сжигая попытку.

## Схема данных

Одна таблица `job_runs` — журнал запусков: имя задачи, статус
(`running` / `success` / `failed`), время начала и конца, длительность,
число обработанных сущностей, текст ошибки и произвольный `meta` в JSONB.
Дашборд считает всю статистику из неё.

Изменили `src/db/schema.ts` → `npm run db:generate` → `npm run db:migrate`.

## Дашборд

- четыре KPI-плитки за сутки со сравнением с предыдущими сутками;
- столбчатая диаграмма запусков по дням, стек «успешно / с ошибкой», подсказка
  при наведении и разворачиваемая таблица с точными значениями;
- разрез по задачам за неделю и журнал последних запусков.

Цвета серий — синий и оранжевый; пара проверена на различимость при
дальтонизме в светлой и тёмной темах. Красно-зелёная пара для этого не
годится, поэтому статусные цвета используются только в бейджах и всегда
вместе с иконкой и подписью. Тёмная тема подобрана отдельно, а не получена
инверсией светлой; переключатель в шапке — «как в системе / светлая / тёмная».

## Справочники

`countries` заполняется из ISO-3166 (250 стран, названия на pt/en/ru).
Сопоставление страны рождения идёт не по точному совпадению, а по
нормализованному ключу через `country_aliases`: в DOU встречаются опечатки
(`Guiná-Bissau`), устаревшая орфография (`Coréia do Sul`) и иные формы
(`Estado da Palestina`, `Belarus`). На 66 наблюдавшихся написаний потребовалось
9 алиасов; `Congo` помечен как неоднозначный — источник не различает Республику
Конго и ДР Конго.

Когда в источнике появится новое написание, оно попадёт в отчёт неопознанных
стран. Проверить и подобрать алиас:

```bash
npx tsx --env-file-if-exists=.env scripts/resolve-reference.ts countries "Новое Название"
```

Затем добавить в `src/db/seeds/country-aliases.ts` и перезалить справочники.

Категорий причин отказа ровно 8, включая «Неясно». Это ограничение не
предметной области, а читаемости графика: на лайн-чарте дрилл-дауна
различимо 6–8 линий. Цветовой слот закреплён за категорией, чтобы столбец
в bar chart и линия в дрилл-дауне были одного цвета.

## Переменные окружения

Все значения — в `.env.example`. Внутри compose `DATABASE_URL` и `REDIS_URL`
подставляются автоматически с хостами `postgres` и `redis`; значения из `.env`
используются при локальном запуске.

| Переменная | Назначение |
|---|---|
| `POSTGRES_USER` / `POSTGRES_PASSWORD` / `POSTGRES_DB` | доступ к БД |
| `POSTGRES_PORT` / `REDIS_PORT` / `WEB_PORT` | порты, видимые с хоста |
| `DATABASE_URL` / `REDIS_URL` | подключения для локального запуска |
| `TZ` | часовой пояс; влияет на группировку статистики по суткам |
| `WORKER_CONCURRENCY` | сколько задач воркер выполняет параллельно (по умолчанию 2) |
