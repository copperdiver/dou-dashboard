# DOU Dashboard

Заготовка приложения: Next.js (App Router) + PostgreSQL, фоновые задачи по
расписанию в отдельном контейнере и дашборд со статистикой их выполнения.

## Стек

| Слой | Решение |
|---|---|
| UI и SSR | Next.js 16 (App Router), React 19, Tailwind CSS 4 |
| БД | PostgreSQL 18, Drizzle ORM + drizzle-kit для миграций |
| Очереди и расписание | BullMQ + Redis 8, воркер в отдельном контейнере |
| Запуск | Docker Compose: `postgres`, `redis`, `migrate`, `web`, `worker` |

## Быстрый старт — всё в Docker

```bash
cp .env.example .env
docker compose up -d --build
```

Дашборд: http://localhost:3000

Что происходит: поднимаются Postgres и Redis, одноразовый сервис `migrate`
включает расширения `pg_trgm`/`unaccent`, применяет миграции, заливает
справочники (250 стран с алиасами, 27 штатов, категории и атомарные причины
отказа) и завершается. Затем стартуют `web` и `worker`.

Справочники — не демо-данные: без них не сопоставляются страна рождения
и штат проживания, поэтому они часть развёртывания, а не отдельный шаг.

## Разработка на хосте

В Docker остаётся только инфраструктура, Next.js и воркер запускаются локально
с hot-reload:

```bash
cp .env.example .env
docker compose -f docker-compose.dev.yml up -d
npm install
npm run db:migrate
npm run db:seed-reference

npm run dev          # терминал 1 — http://localhost:3000
npm run worker:dev   # терминал 2 — фоновые задачи
```

## Конвейер загрузки

Прогресс живёт в таблицах Postgres, а BullMQ — только будильник. Каждая
задача — идемпотентный насос: забирает пачку работы через
`for update skip locked`, обрабатывает и завершается. Перезапуск воркера
или `docker compose down -v` для Redis не рушат бэкфилл на 250 дней.

| Насос | Очередь | Что делает |
|---|---|---|
| `discover` | jobs | ставит в `ingest_days` дни за последнюю неделю |
| `enumerate` | fetch | дневной индекс → снапшот `jsonArray` → список статей |
| `fetch` | fetch | загрузка страниц в `source_page_html` |
| `parse` | jobs | акты, люди, решения; помечает день в `dirty_days` |
| `canonize` | jobs | причины отказа правилами и декодером правовых ссылок |
| `enrich` | llm | остаток причин через LLM |
| `rollup` | jobs | пересчёт суточных витрин по дням из `dirty_days` |

Очереди разделены по классу ресурса, а не по шагу: в BullMQ concurrency и
limiter задаются на Worker. `dou-fetch` — единственная, что ходит в сеть:
concurrency 1 и один запрос в 2 секунды. У насосов `attempts: 1` —
«повтор» это следующий тик крона, а учёт попыток по единице работы живёт
в самой таблице (`attempts`, `next_attempt_at`).

Сбои различаются по типу, а не сваливаются в один ретрай:

| Ответ источника | Реакция |
|---|---|
| 403 / 429 | пауза всей очереди `dou-fetch`; попытка не сжигается; серия из 3 → пауза на час |
| 404 / 410 | `fetch_status='gone'`, больше не пытаться |
| 5xx, таймаут | экспоненциальный backoff, после 5 попыток `failed` |
| 200 без `script#params` | `failed` с явным «разметка изменилась» — этот сигнал нельзя глушить ретраями |
| дневной индекс пуст | `no_edition` (выходные, праздники), а не `failed` |

Бэкфилл и инкрементальный опрос — один и тот же код. Различаются только
`origin` (для отчётности) и `priority`: насос берёт
`order by priority, edition_date desc`, поэтому свежий день никогда
не ждёт, пока дожуётся история.

Один прогон насоса — одна строка в `job_runs`; детали в `meta`
(`{days, pages, noEdition, failures, schemaMismatch}`). Журналом
элементов `job_runs` не становится.

Захват работы обязан **менять** строку, а не только блокировать её.
Одного `for update skip locked` мало: блокировка снимается с концом
запроса, и два насоса берут одни и те же строки. Поэтому статус
переводится в `running` с арендой по времени — упавший процесс не держит
работу дольше аренды.

## Разбор страниц

Тип акта определяется **по содержимому**, а не по заголовку. Заголовки
ненадёжны: `PORTARIA 6.375` без `Nº`, `Despachos` в разном регистре,
одобрение внутри despacho как `Assunto: Deferimento`.

Что ловится и почему это важно:

| Случай | Как обрабатывается |
|---|---|
| `CERTIFICO … passou a assinar` | смена имени, а не одобрение: строка выглядит как строка о человеке |
| `Requerente: … LTDA`, `Prazo: 2 Anos` | разрешение на работу из того же департамента — не натурализация |
| `Manutenção de Indeferimento` | подтверждение прежнего отказа, в счётчик новых отказов не идёт |
| `Tornar sem efeito o Recurso de Manutenção` | отмена решения; проверяется **раньше** `manutenção`, иначе считалось бы подтверждением |
| `Arquivamento do pedido` | производство прекращено, а не отказано по существу |
| `Igualdade de Direitos`, `Reaquisição` | другие процедуры: `subject_kind` не `naturalization` |

Метки блоков и поля людей встречаются в разных написаниях, и каждая
непокрытая форма теряла запись целиком, а не портила одно поле:
`Interessado:` / `Interessada:` / `Interessado(a):`, `Processo nº:` с «nº»
перед двоеточием, `natural doa` вместо `dos`, номер документа словом
`RNM`, отсутствие запятой перед `nascido`. Порядок полей в блоке тоже не
фиксирован — граница блока определяется по повторению уже заполненной
метки.

Не разобранный абзац не выбрасывается, а попадает в счётчик
`unparsed`: молчаливая потеря человека — худший возможный отказ парсера.

Диагностика:

```bash
npx tsx --env-file-if-exists=.env scripts/parse-report.ts --verbose
npx tsx --env-file-if-exists=.env scripts/survey-blocks.ts
npm test
```

`parse-report.ts` прогоняет парсер по уже загруженным страницам, ничего
не записывая — так видно последствия правок до того, как они попадут
в данные. `survey-blocks.ts` показывает, какие метки, значения `Assunto`
и формы номеров реально встречаются: правила опираются на замер, а не на
догадку. Тесты идут на фикстурах из реальных страниц
(`tests/fixtures/dou/`), обновляются через `scripts/save-fixtures.ts`.

При изменении правил разбора увеличьте `PARSER_VERSION` в
`src/worker/pumps/parse.ts` — страницы с меньшим значением переразберутся
автоматически. Переразбор не удаляет записи, а сопоставляет их по хешу
абзаца и `codigo`; исчезнувшие помечаются `retired_at`.

## Как добавить фоновую задачу

1. Опишите её в `SCHEDULE` в `src/worker/jobs.ts` — имя, очередь,
   cron-выражение, описание.
2. Добавьте обработчик в `handlers` под тем же именем.
3. Перезапустите воркер — расписание синхронизируется автоматически,
   удалённые из `SCHEDULE` задачи снимаются с расписания.

```ts
// src/worker/jobs.ts
export const SCHEDULE = [
  { name: 'import-orders', queue: 'jobs', pattern: '*/10 * * * *', description: 'Импорт заказов' },
]

export const handlers = {
  async 'import-orders'({ log }) {
    const orders = await claimOrders() // работу берём из БД, а не из payload
    log(`получено ${orders.length}`)
    return { itemsProcessed: orders.length, meta: { orders: orders.length } }
  },
}
```

Насос обязан быть идемпотентным и брать работу из БД, а не из payload
задания: только тогда лишний или повторный запуск безвреден, а прогресс
переживает потерю Redis. Если источник попросил подождать, верните
`cooldownMs` — воркер поставит очередь на паузу, не сжигая попытку.

## Причины отказа

Причина — **атомарная**, связь с отказом многие-ко-многим. Текст причины
по тексту не сматчить: 267 отказов дают 203 уникальных текста, а внутри
одного текста обычно несколько причин.

Порядок разрешения — от дешёвого к дорогому, по **уникальным текстам**,
а не по отказам:

1. **Дедупликация.** `reason_texts` хранит уникальный нормализованный
   текст; правила и LLM видят каждый текст один раз.
2. **Правила** (`src/lib/reasons/rules.ts`, ~12 регулярок) — по клаузам,
   со спанами-доказательствами.
3. **Декодер правовых ссылок** (`legal-refs.ts`). Ссылка на статью —
   контекст, а не причина: `art. 65` есть в 74% текстов, и будь он
   причиной, крупнейшая категория графика была бы пустой по смыслу.
   Но номер `inciso` называет конкретное требование: `art. 65` — I
   дееспособность, II срок проживания, III португальский язык,
   IV судимости. Сопоставлены только инцизы, чей смысл подтверждён
   и текстом закона, и наблюдавшимися формулировками.
4. **LLM** — только непокрытый остаток, а не весь текст.

Замер на 267 реальных текстах: правила и декодер покрывают **94%**,
в LLM уходит 6%.

### Провайдер LLM

`LLM_PROVIDER=auto|claude|openai|noop`.

| Значение | Поведение |
|---|---|
| `auto` (по умолчанию) | claude при `ANTHROPIC_API_KEY`, иначе openai при `OPENAI_API_KEY`, иначе заглушка |
| `claude` | Claude, модель из `LLM_MODEL_CLAUDE` (по умолчанию `claude-opus-5`) |
| `openai` | OpenAI Responses API, модель из `LLM_MODEL_OPENAI` (по умолчанию `gpt-5.2`) |
| `noop` | без обращений к LLM |

Ключи живут в `.env` — он в `.gitignore`; шаблон в `.env.example`. Отдельный
файл вида `.env.keys` не подойдёт: ни docker compose, ни Next.js его сами
не читают.

Без ключей конвейер работает на заглушке, а не падает: загрузка и разбор
от LLM не зависят. Заглушка сохраняет португальский оригинал и **не
придумывает переводов** — поддельный перевод в UI выглядит так же
авторитетно, как настоящий. Непонятые тексты остаются в `needs_review`
и видны на экране health.

Явно указанный провайдер без ключа — ошибка конфигурации, воркер скажет
об этом сразу. А вот в режиме `auto` посторонний `ANTHROPIC_API_KEY`
в окружении шелла перебьёт `OPENAI_API_KEY`: если нужен именно OpenAI,
задайте провайдера явно.

Промпт, схема ответа и разбор — общие для провайдеров
(`src/lib/llm/prompt.ts`). Иначе формулировки разойдутся и разница
в качестве спишется на модель вместо промпта. Модель задаётся отдельной
переменной на провайдера: общая уехала бы в чужой API и дала бы там 404.

Правила живут в коде, а не в БД: их надо ревьюить, тестировать на
фикстурах и откатывать. При изменении увеличьте `RULES_VERSION` —
тексты переразберутся. Переразбор снимает только автоматические связи;
`method='manual'` неприкосновенны.

Диагностика без записи в БД:

```bash
npx tsx --env-file-if-exists=.env scripts/reasons-report.ts --show-remainder
```

**Метрика bar chart — `count(distinct denial_id)` на категорию.** У отказа
до нескольких причин из разных категорий, поэтому сумма по столбцам не
равна числу отказов (на текущих данных 555 против 250). Подпись
обязательна: «отказов, затронутых категорией».

## Суточные витрины

Витрины нужны **не для скорости**: на таком объёме любой график считается
за единицы миллисекунд по индексам. Они нужны для трёх других вещей.

**Единое определение «нового отказа».** Оно живёт в
`denials.counts_as_new_denial`, а не размазано по запросам: подтверждение
отказа при обжаловании и повторная публикация в счёт не идут.

**Различение «нет данных» и «ноль».** `daily_stats.coverage` берётся из
`ingest_days`, а не из фактов:

| coverage | Что значит |
|---|---|
| `covered` | день загружен и разобран |
| `no_edition` | выпуска не было (выходные, праздники) |
| `missing` | день не загружен |

**Фронтенд обязан рисовать разрыв линии на `missing`/`no_edition`, а не
нулевую точку** — иначе график врёт, и вся эта работа напрасна.

**Дрилл-даун «категория × день»** без join через три таблицы на каждую
точку графика.

Пересчёт инкрементальный: `parse` и `canonize` помечают затронутые дни
в `dirty_days`, `rollup` их разбирает. Пересчёт дня — удаление и вставка
в одной транзакции, то есть идемпотентно. Полный ребилд — засеять
`dirty_days` нужным диапазоном:

```sql
insert into dirty_days (day, reason)
select generate_series('2025-08-01'::date, current_date, '1 day')::date, 'rebuild'
on conflict (day) do nothing;
```

Границы возрастных групп заданы **один раз** — в `AGE_BUCKET_SQL`
(`src/worker/pumps/rollup.ts`) плюс перечисление в enum `age_bucket`.
Функции на TypeScript для них нет сознательно: UI читает готовые группы
из витрины, а два определения одних и тех же границ разошлись бы.

Сумма гистограммы возрастов меньше числа одобрений на количество людей
без даты рождения (в источнике такие есть). Разницу нужно показывать
в UI, иначе несходящаяся сумма читается как баг.

## Схема данных

Одна таблица `job_runs` — журнал запусков: имя задачи, статус
(`running` / `success` / `failed`), время начала и конца, длительность,
число обработанных сущностей, текст ошибки и произвольный `meta` в JSONB.
Дашборд считает всю статистику из неё.

Изменили `src/db/schema.ts` → `npm run db:generate` → `npm run db:migrate`.

## Дашборд

- четыре KPI-плитки за сутки со сравнением с предыдущими сутками;
- столбчатая диаграмма запусков по дням, стек «успешно / с ошибкой», подсказка
  при наведении и разворачиваемая таблица с точными значениями;
- разрез по задачам за неделю и журнал последних запусков.

Цвета серий — синий и оранжевый; пара проверена на различимость при
дальтонизме в светлой и тёмной темах. Красно-зелёная пара для этого не
годится, поэтому статусные цвета используются только в бейджах и всегда
вместе с иконкой и подписью. Тёмная тема подобрана отдельно, а не получена
инверсией светлой; переключатель в шапке — «как в системе / светлая / тёмная».

## Справочники

`countries` заполняется из ISO-3166 (250 стран, названия на pt/en/ru).
Сопоставление страны рождения идёт не по точному совпадению, а по
нормализованному ключу через `country_aliases`: в DOU встречаются опечатки
(`Guiná-Bissau`), устаревшая орфография (`Coréia do Sul`) и иные формы
(`Estado da Palestina`, `Belarus`). На 66 наблюдавшихся написаний потребовалось
9 алиасов; `Congo` помечен как неоднозначный — источник не различает Республику
Конго и ДР Конго.

Когда в источнике появится новое написание, оно попадёт в отчёт неопознанных
стран. Проверить и подобрать алиас:

```bash
npx tsx --env-file-if-exists=.env scripts/resolve-reference.ts countries "Новое Название"
```

Затем добавить в `src/db/seeds/country-aliases.ts` и перезалить справочники.

Категорий причин отказа ровно 8, включая «Неясно». Это ограничение не
предметной области, а читаемости графика: на лайн-чарте дрилл-дауна
различимо 6–8 линий. Цветовой слот закреплён за категорией, чтобы столбец
в bar chart и линия в дрилл-дауне были одного цвета.

## Переменные окружения

Все значения — в `.env.example`. Внутри compose `DATABASE_URL` и `REDIS_URL`
подставляются автоматически с хостами `postgres` и `redis`; значения из `.env`
используются при локальном запуске.

| Переменная | Назначение |
|---|---|
| `POSTGRES_USER` / `POSTGRES_PASSWORD` / `POSTGRES_DB` | доступ к БД |
| `POSTGRES_PORT` / `REDIS_PORT` / `WEB_PORT` | порты, видимые с хоста |
| `DATABASE_URL` / `REDIS_URL` | подключения для локального запуска |
| `TZ` | часовой пояс; влияет на группировку статистики по суткам |
| `WORKER_CONCURRENCY` | сколько задач воркер выполняет параллельно (по умолчанию 2) |
